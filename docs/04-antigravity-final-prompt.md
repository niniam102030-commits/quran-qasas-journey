# پرامپت نهایی برای ایجنت Antigravity — تکمیل، رفع باگ و آماده‌سازی انتشار

> این پرامپت را کامل به ایجنت بدهید. ایجنت **دسترسی به ترمینال، مرورگر و وب** دارد. هدف: پروژه بدون باگ، قابل نصب روی اندروید و آماده‌ی استفاده شود. ایجنت تا برقرارشدن «معیار پایان» (بخش ۸) متوقف نشود.

## 0) زمینه
پروژه‌ی `D:\Quran\قصص`: اپ فارسی RTL و آفلاین برای حفظ ۸۸ آیه‌ی سوره‌ی قصص (مصحف مدینه، ترجمه‌ی انصاریان، معنای تک‌تک کلمات). واحد یادگیری = نیم‌صفحه‌ی مصحف (۲۲ واحد). پشته: React 19، TypeScript، Vite، Tailwind 3، Zustand، Dexie 4، ts-fsrs 6، Capacitor، vitest.
اسناد مرجع (اول بخوان): `docs/00-راهنمای-اجرا.md`، `01-content-prompt.md`، `02-antigravity-spec.md`، `DECISIONS.md`، `docs/03-remaining-work.md`.

**آنچه قبلاً نوشته شده ولی هرگز اجرا/کامپایل نشده است** (نویسنده به ترمینال دسترسی نداشت؛ پس خطای تایپ، import و منطق محتمل است):
- `scripts/merge-parts.mjs`، `validate-content.mjs` (پرچم `--merged`)، `validate-deep.mjs`، `build-manifest.mjs`
- `src/learning/{cardScheduler,mastery,sessionPlanner}.ts` و `src/learning/__tests__/learning.test.ts`
- `src/db/learningDb.ts` (Dexie جدید `QasasLearningDB`)، `src/services/contentLoader.ts`
- `src/store/useLearningStore.ts`، `src/components/learning/QuestionRenderer.tsx`
- `src/pages/{LearningSessionPage,UnitsPage}.tsx` و اتصال آن‌ها در `src/App.tsx`
- اصلاح `src/services/grading.ts` (perTarget فقط برای پاسخ دقیق درست)

## 1) قوانین سخت (نقض‌ناپذیر)
1. متن قرآن هرگز در `src/` هاردکد نشود؛ فقط از `public/content/**` خوانده شود.
2. تصحیح فقط با شناسه/اندیس (id/index) باشد؛ هرگز مقایسه‌ی رشته‌ی عربی.
3. ترجمه فقط انصاریان؛ معنای کلمات را از خودت نساز. هر «بخشی از آیه در ترجمه انصاریان»-گونه (متن ساختگی) ممنوع.
4. کلیدهای کارت: `w:`، `vr:`، `vt:`، `vn:`، `sq:`، `pg:`؛ FSRS: ماندگاری ۰.۹۳ (vr/vn/sq/pg) و ۰.۹۰ (w/vt)، سقف ۱۲۰ روز، fuzz خاموش.
5. فایل‌های اصلی در `public/content/units/` را تغییر نده؛ خروجی ادغام فقط در `public/content/merged/`.
6. هر تغییر ← `npm run build`، `npm run lint` و `npm test` سبز بماند.

## 2) گام A — خط لوله‌ی محتوا
1. `npm install`
2. `node scripts/merge-parts.mjs` → `docs/merge-report.md` را بخوان. هر «مشکل» (کلمه‌ی بدون lexicon، آیه‌ی بدون chunk، سهمیه‌ی مرحله‌ی ۸ کمتر از `max(30, 8×آیه)`، مرحله‌ی خالی) باید برطرف شود.
3. `node scripts/validate-content.mjs --merged --strict` و `node scripts/validate-deep.mjs --strict`. گزارش: `docs/validation-report.md`.
4. اگر `validate-deep` خطای **کاذب** داد (مثلاً نام فیلدهای `stem.num`، `givenCount`، `wordRange`، `hiddenIdx` با ساختار واقعی فایل‌ها نمی‌خواند)، ابتدا ساختار واقعی را از چند فایل نمونه در `public/content/units/` بخوان و **اسکریپت را اصلاح کن**، نه محتوا را.
5. برای خطای **واقعی** (پاسخ نادرست، ترتیب غلط، گزینه‌ی تکراری، شماره‌ی آیه‌ی غلط، `sq` برای آیه‌ی ۸۸، `faSegments` ناهمخوان با ترجمه): سوال را مستقیماً در فایل اصلی `units/…` اصلاح کن، یا اگر ساخت درست نیازمند بازتولید است، با رعایت `docs/01-content-prompt.md` سوال جایگزین بنویس (با شناسه‌ی یکتا و ادامه‌ی شماره‌گذاری). فقط سوال‌های خطادار را دست بزن.
6. تکرار تا هر دو اعتبارسنج بدون خطا شوند. سپس `node scripts/build-manifest.mjs`.
7. **بازبینی کیفی نمونه‌ای**: از هر واحد ۱۰ سوال تصادفی و ۱۰ واژه‌ی lexicon را با منبع معتبر (ترجمه‌ی انصاریان در سایت‌هایی چون tanzil.net / quran.com و لغت‌نامه‌ی معتبر) تطبیق بده. هرگونه معنای مشکوک را در `docs/review-flags.md` با ارجاع منبع فهرست کن و اصلاح کن.

## 3) گام B — کامپایل، لینت و تست
1. `npm run build`؛ همه‌ی خطاهای TypeScript را در فایل‌های بخش ۰ رفع کن (احتمالاً: سازگاری با ts-fsrs 6، تایپ `Question` در `src/types/learning.ts` برای `QuestionRow`، `import.meta.env`، تایپ ایندکس `[unitId+stage]`).
2. `npm run lint` و `npm test`. اگر تستی ناسازگار با رفتار درست بود، **ابتدا مشخصات را بسنج** و سپس کد یا تست را اصلاح کن (نه فقط تست را برای سبزشدن تغییر بده).
3. تست‌های بیشتر بنویس: `grading.ts` (۴ شکل، پاسخ ناقص ⇒ perTarget همه false)، `contentLoader` (با fake-indexeddb: همگام‌سازی دوباره cards/attempts را پاک نکند)، `useLearningStore` (غلط ⇒ صف مجدد +۳ و +۷؛ پایان مرحله ⇒ unitProgress؛ مرحله‌ی ۸ + بدهی <۴۰ ⇒ بازشدن واحد بعدی).

## 4) گام C — تکمیل برنامه (طبق `02-antigravity-spec.md` و `03-remaining-work.md`)
اولویت از بالا:
1. **قفل ترتیب سوال در جلسه** (`sessionPlanner.ts` / store): مرحله‌ی ۱: هر واژه‌ی جدید سه مواجهه حدود سوال‌های ۱، ۴، ۹ (`EXPOSURE_SLOTS`)؛ ۲۰٪ مرور درهم؛ نردبان سختی بر پایه‌ی ثبات کارت؛ هیچ دو سوال هم‌نوع پشت‌سرهم (مگر ناچار)؛ سوال غلط +۳ و سپس +۷.
2. **میانه‌ی واقعی زمان پاسخ** هر نوع سوال از جدول `attempts` به‌جای عدد ثابت ۵۰۰۰ در `useLearningStore.submit` (برای نگاشت easy/hard).
3. **نیم‌صفحه‌ی مصحف** (`MushafHalfPage`): نمایش آیات واحد با فونت KFGQPC Hafs و شماره‌ی آیه؛ قابلیت مخفی‌کردن بخشی از متن برای تمرین.
4. **صفحه‌ی تسلط** (`MasteryPage`): آیه‌های طلایی (۴ مهارت vr/vt/vn/sq سطح ۳)، نمودار پیشرفت هر واحد، فهرست اشتباهات پرتکرار از جدول `confusions`.
5. **چراغ‌های غیرمسدودکننده** (lamps): هشدار «مرور سررسید دارید»، «واحد قفل است چون بدهی ≥ ۴۰»، بدون بلاک‌کردن جریان.
6. **صفحه‌ی تنظیمات**: اندازه‌ی فونت عربی، روشن/تاریک، صدا/لرزش، ریست پیشرفت (با تأیید دوباره)، خروجی/ورودی پشتیبان JSON از `cards/attempts/unitProgress`.
7. **UX سوال‌ها**: فیدبک درست/غلط با `explanationFa`، نمایش پاسخ درست پس از غلط، پشتیبانی کامل RTL و لمسی، حالت راهنما (usedHint ⇒ حداکثر rating=hard)، تمام شکل‌های choice/match/order/cloze روی موبایل ۳۶۰px بدون سرریز.
8. **پاک‌سازی**: کامپوننت‌ها/صفحات قدیمی (`LessonSessionPage`، چالش‌های قدیمی، `seedInitialDatabase`، `qasas_full_seed.json`، `compile-content-pack.mjs`) را به `legacy/` منتقل کن و فقط در صورت نبود ارجاع زنده حذف کن. `useAppStore.initApp` نباید دیگر وابسته به seed قدیمی باشد؛ `MapPage` و `ChillehProfilePage` یا به داده‌ی جدید وصل شوند یا با صفحه‌های جدید جایگزین شوند.

## 5) گام D — فونت و منابع (نیازمند وب)
1. فونت **KFGQPC Hafs Uthmanic Script** را از منبع رسمی مجمع ملک فهد (qurancomplex.gov.sa) بگیر؛ شرایط مجوز را بخوان و در `docs/licenses.md` ثبت کن. اگر استفاده‌ی مستقیم مجاز نبود، جایگزین با مجوز آزاد (مثلاً Amiri Quran) و ثبت دلیل. فونت را محلی در `public/fonts/` قرار بده و با `@font-face` بارگذاری کن (آفلاین).
2. وضعیت مجوز **ترجمه‌ی انصاریان** و **متن مصحف مدینه** را بررسی و در `docs/licenses.md` بنویس (منبع داده‌ی پایه در `scripts/fetch-base-data.mjs`). اگر محدودیت انتشار عمومی دارد، در گزارش نهایی صریح هشدار بده.
3. هماهنگی متن پایه با منبع معتبر: ۸۸ آیه‌ی `qasas.base.json` را با tanzil (uthmani) مقایسه کن و هر اختلاف را گزارش/اصلاح کن.

## 6) گام E — تست رفتاری واقعی
با مرورگر (Playwright یا دستی) روی `npm run dev` و `npm run preview`:
1. نصب تازه: پاک‌کردن IndexedDB ← بارگذاری ← `syncContent` بدون خطا ← ۲۲ واحد در `UnitsPage`، فقط واحد ۱ باز.
2. اجرای کامل مرحله‌ی ۱ تا ۸ واحد اول، با پاسخ‌های درست؛ سپس سناریوی غلط (صف مجدد)، راهنما، تغییر پاسخ. بررسی ثبت `cards`/`attempts`/`confusions`/`unitProgress` در IndexedDB.
3. شبیه‌سازی گذر زمان (دست‌کاری `due`) ← «مرور روزانه» ← کاهش بدهی.
4. بدهی ≥ ۴۰ ⇒ واحد بعدی بسته می‌ماند؛ <۴۰ ⇒ باز می‌شود.
5. آفلاین (قطع شبکه / Service Worker اگر دارید): همه چیز کار کند.
6. دکمه‌ی «مرور روزانه» وقتی بدهی صفر است غیرفعال باشد؛ جلسه‌ی خالی نباید کرش کند.
7. هر باگی که یافتی را با تست خودکار ثبت و رفع کن.

## 7) گام F — Android
`npm run cap:build` ← `npx cap open android` یا ساخت مستقیم APK debug با Gradle. اجرا روی شبیه‌ساز/دستگاه: فونت عربی، RTL، صفحه‌کلید، دکمه‌ی back، ذخیره‌ی IndexedDB پس از بستن برنامه. آیکون/اسپلش/نام برنامه (به فارسی) را تنظیم کن. APK debug را در `release/` بگذار و مراحل امضای release را در README بنویس.

## 8) معیار پایان (همه باید برقرار باشد)
- `npm run content:all`، `npm run build`، `npm run lint`، `npm test` همگی بدون خطا.
- هر ۲۲ واحد: lexicon کامل، chunks همه‌ی آیه‌ها، مراحل ۱ تا ۸ پُر، سهمیه‌ی مرحله‌ی ۸ رعایت‌شده، صفر خطای اعتبارسنج عمیق.
- تست رفتاری بخش ۶ بدون باگ؛ هیچ خطای console در جریان اصلی.
- `docs/licenses.md`، `docs/review-flags.md` و `README.md` (راه‌اندازی، تولید محتوا، ساخت APK) نوشته شده.
- گزارش نهایی: فهرست تغییرات، باگ‌های یافته/رفع‌شده، موارد باز (اگر هست) با دلیل.

اگر در هر گام به تصمیم محصولی برخوردی که در اسناد نیست، گزینه‌ی سازگار با `DECISIONS.md` را انتخاب کن و در `DECISIONS.md` ثبت کن؛ فقط برای مجوز/حقوقی از کاربر بپرس.
